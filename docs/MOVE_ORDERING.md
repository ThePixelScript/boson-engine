# Boson Move Ordering Architecture and Telemetry

## 1. Pipeline Architecture: Generator $\to$ Orderer $\to$ Search

In alpha-beta minimax search, node count is bounded below by the minimal tree size $O(b^{d/2})$ under optimal move ordering, compared to $O(b^d)$ under random ordering. Boson strictly separates generation, ordering, and search into distinct architectural layers:

```
+---------------------+
|    MoveGenerator    | Layer 2 / Layer 3: Populates pseudo-legal or legal MoveList
+---------------------+
           |
           v
+---------------------+
|     MoveOrderer     | Scores candidates using purely structural & heuristic bands
+---------------------+
           |
           v
+---------------------+
|    Search::negamax  | Iterates candidates in-place; executes alpha-beta cutoffs
+---------------------+
```

### Architectural Invariants
1. **Decoupling from Evaluation**: `MoveOrderer` never queries `Evaluator::evaluate()` and computes zero positional terms. All heuristic bonuses derive strictly from move metadata, static exchange evaluations (SEE), transposition lookups, and historical cutoffs.
2. **Move Preservation**: Ordering operates in-place on a fixed stack buffer (`std::array<int, 256>`). It never adds, drops, duplicates, or mutates any `Move` generated by `MoveGenerator`.
3. **Zero Dynamic Allocation**: Scoring and sorting execute within stack limits, guaranteeing zero heap pressure during tree traversal.

## 2. Scoring Taxonomy and Priority Stratification

Every move is assigned an integer score within strictly non-overlapping priority bands:

| Priority Band | Score Range | Description |
|---|---|---|
| **1. TT Move** | `100,000` | Best move returned by Transposition Table probe (PV or cutoff move from earlier/deeper iteration). |
| **2. Winning & Equal Captures** | `50,100 .. 50,605` | Captures with static exchange evaluation $\text{SEE} \ge 0$, stratified by MVV-LVA (Most Valuable Victim - Least Valuable Attacker). |
| **3. Promotions** | `40,000` | Pawn advances reaching the 8th rank. |
| **4. Killer Move 1** | `30,000` | Primary quiet move that caused a beta cutoff at the current search ply. |
| **5. Killer Move 2** | `29,000` | Secondary quiet move that caused a beta cutoff at the current search ply. |
| **6. Countermoves** | `28,000` | Quiet move stored in Counter-Move History table keyed by opponent's prior move `(from, to)`. |
| **7. History & Continuation** | `1 .. 20,000` | Quiet moves weighted by butterfly history and continuation history, clamped below countermoves. |
| **8. Quiet Moves** | `0` | Unscored neutral quiet moves. |
| **9. Losing Captures** | `< -20,000` | Captures with $\text{SEE} < 0$ (e.g. $Q \times P$), demoted below all quiet candidates and ordered by least negative SEE loss. |

## 3. Table Ownership & Lifecycle Invariants

### 3.1 Killer Table
- **Layout**: `std::array<std::array<Move, 2>, 64>` (2 quiet move slots per ply, up to `MAX_PLY = 64`).
- **Update Rule**: On quiet beta cutoffs (`alpha >= beta`), if `m != killer[ply][0]`, slot 0 shifts to slot 1, and slot 0 is updated to `m`.
- **Filtering**: Tactical captures and promotions are excluded from the killer table.
- **Ownership**: Owned statically by `Search`. Cleared at the inception of each `Search::runSearch()` invocation.

### 3.2 Butterfly History Table
- **Layout**: `std::array<std::array<uint32_t, 64>, 12>` indexed by `[PieceType][ToSquare]`.
- **Update Rule**: On quiet beta cutoffs, incremented with depth-squared bonuses ($bonus = \text{depth}^2$).
- **Gravity Damping**: Values are clamped to $[-16384, 16384]$ using saturating exponential decay to prevent counter overflow and favor recent search tree activity.
- **Ownership**: Owned statically by `Search`, zeroed upon new search initialization.

### 3.3 Counter-Move and Continuation History Tables
- **Counter-Move History**: `CounterMoveTable` maps `[FromSquare][ToSquare]` of the preceding ply's move to the refutation move.
- **Continuation History**: `ContinuationHistoryTable` tracks pair correlations between prior piece placements and subsequent quiet responses.
- **Ownership**: Owned by `Search`. State is reset cleanly prior to iterative deepening.

## 4. Telemetry and Benchmarking Diagnostics

`SearchController` aggregates search telemetry across every iteration:
1. **TT Efficiency**:
   - `ttHits`: Number of successful hash lookups that resolved cutoffs or supplied candidate moves.
2. **Cutoff Distribution**:
   - `betaCutoffs`: Total fail-high events across all plies.
   - `cmhCutoffs` & `conthistCutoffs`: Proportion of cutoffs triggered directly by countermoves or continuation history.
3. **Speed & Throughput**:
   - Total nodes (`nodes` + `qNodes`), elapsed time (ms), and Nodes Per Second (NPS).
4. **Pruning & Reduction Efficiency**:
   - `nullCutoffs` / `nullAttempts` (Null Move Pruning effectiveness).
   - `successfulResearches` / `lmrAttempts` (LMR accuracy and overturn rate).
